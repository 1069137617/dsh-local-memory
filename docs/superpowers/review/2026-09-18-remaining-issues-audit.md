## 一、跨进程删除被复活（🔴 新发现，优先级最高）

### 为何这是新问题

README（两版 L59）承认的边界是：

> 若一方删除某条目，而另一方**恰好并发持有该条目且时间戳更新**，则删除可能失败、条目存活。

即把失败条件限定为"对手持有**更新**的时间戳"。实测该限定**不成立**——对手只需**持有旧副本**即可让删除失效，无需更新的时间戳。

### 机制

`src/store.ts:227-249` `mergeFromDisk()` 是**并集**语义：磁盘上有的 id 并入本地，本地有的保留。但本地**删除**后磁盘上没有该 id 时，代码不会把本地内存里的该条移除（`local` Map 由 `this.entries` 构建，而 `this.entries` 仍持有它），于是：

1. A 删除 → 磁盘无该条；
2. B（load 较早、内存仍持有该条）做**任意一次写入**（哪怕是新增自己的条目）；
3. B 的 flush 在锁内 `mergeFromDisk()` → B 的 `entries` 仍含 victim → 整体写回磁盘；
4. **victim 复活**，A 的删除永久丢失。

`tombstones` 只在**删除方自己**的进程内有效（`store.ts:60` 是实例字段，非持久化），管不到对手进程。

### 实测（真实 `spawn`）

```
A 建库后磁盘: ["victim-条目"]
B 已启动并 load（内存中持有 victim）
A 删除后磁盘: []
B 退出码: 0
最终磁盘: ["victim-条目","B-新条目"]

判定 删除是否被复活 : ★ 复活了 —— 删除丢失
     B 是否持有更新戳 : 否（B 只是持旧副本、updatedAt 更早）
```

### 影响

用户/agent 删除一条记忆（如"这条是错的，删掉"），只要当时有另一个 DSH 实例（另一窗口、web + CLI 并行）被打开过，该条目会在对手下次写入时**无声复活**。用户会认为"删不掉"。

### 建议

- **最小改法**：`mergeFromDisk()` 补**差集**语义——本地 `entries` 中的 id 若不在磁盘且**本地未在本次 mutate 中新增它**，则应视为"对手已删除"并移除。需要区分"本地新增（尚未落盘）"与"本地持有（曾落盘）"，可引入 `dirtyIds` / `knownOnDisk` 集合。
- **更稳的改法**：把 tombstone **持久化**（如 `entries.jsonl.tombstones` 或条目内 `deletedAt` 软删标记），使删除意图跨进程可见。
- 无论哪种，**必须**配真实 spawn 的回归测试（现为零覆盖）。

> ⚠️ 注意：README L59 的措辞**低估了**这个问题，不能靠改文档收尾——它是数据一致性问题，不是措辞问题。

## 二、读路径永久陈旧（🔴 新发现）

### 机制

`load()` 全仓仅 `index.ts:32` 一处调用（上一轮已核实）；此后 `snapshot()` / `revision()` 全从内存 `this.entries` 算。`mergeFromDisk()` **只在 `flush()` 内**被调用（`store.ts:178`）——即**只有写操作才会重读磁盘**。

于是纯读路径（每轮注入 `renderSnapshot(store.snapshot(), …)`、`local_memory_search`）在进程生命周期内**永远看不到对手写入的条目**。

### 实测（真实 `spawn`）

```
A 新增一条后磁盘: ["A-第一条","A-第二条"]  revision=34aeb2031faf（A 侧）
B 报告（同一进程内前后两次读）：
   B 首次 load 条目数 before=1
   A 写入后 B 再读条目数 after=1
   B 磁盘上实际行数 2

判定 B 是否感知 A 的写入 : ★ 未感知 —— B 的注入/检索永远缺这条
```

交叉验证：B **主动写一次**后，`mergeFromDisk` 会把 A 的条目补上（`A-后来又写` 出现了）——**证明陈旧只在"纯读"期间存在**，进一步确认根因是"只在 flush 内合并"。

### 影响

多实例场景下，实例 B 的记忆库**冻结在启动那一刻**（直到它自己写一次）。A 写入的关键记忆（如"这个仓库的部署方式"）在 B 中**永远检索不到**，且 B 的每轮注入也持续缺失。用户视角："我在另一个窗口存的记忆，这边搜不到。"

### 建议

- 在 `snapshot()` 前加**带节流的重读**（如 `mtime` / `size` 变化才 `mergeFromDisk`，避免每轮注入都读盘）；
- 或至少在 `local_memory_search` 路径上强制重读一次（检索本就低频，代价可接受）；
- 上一轮的乐观锁"跨进程失明"与本条**同源**，可一并解决（重读后 `revision()` 自然反映对手写入）。

> 与问题一的关系：两者都出在"合并只在 flush 内发生"。若按问题一的建议引入 `knownOnDisk`，可顺带把合并提到读路径。

## 三、P2 未闭合：写入即失明（🟠 确认仍存在）

上一轮核对文档第五节把它标为"**代码路径推导**，未实机验证"。本轮已**实机验证**，并确认 `validateConfig` 不拦截该组合。

### 实测

```
add 回执（tools.ts 同款取值）: id=b4e14000c2aa  text.length=300
写入是否成功            : 成功（会被回执为 committed）
注入快照内容            : "LOCAL MEMORY SNAPSHOT (revision 50e055571e3e; …)\n(0 of 1 entries fit the 200-char budget — call local_memory_search)"
该条是否出现在注入中    : 未出现 —— 写入即失明
store 内条目数          : 1（数据没丢，只是永远注入不出来）

附带  该组合能否通过 validateConfig：
maxInjectionChars=200, entryMaxChars=8000 : 通过
maxInjectionChars=4000, entryMaxChars=8000: 通过
```

### 要点

- `validateConfig`（`config.ts:38-39`）对两者**独立**校验，无交叉约束，故用户可在设置页合法存下该组合；
- `render.ts:41` 是"整条放不下就跳过、条内不截断"，于是超预算条目**永远**进不了注入；
- 更隐蔽的是：`add` **照常回执 `committed`**，而失败提示行只说"call local_memory_search"——agent 会以为自己记住了，此后每轮都看不到。

### 建议（P2 原文，仍适用）

二者其一：① `validateConfig` 补交叉约束（如 `entryMaxChars <= maxInjectionChars - 余量`）；② `render.ts` 对单条超预算做**截断**而非纯跳过。推荐 ②，因为它同时修掉"合法但边缘配置"下的不可见问题，且不限制用户配置自由。

### 4c. 发现 3（分组头 `used` 跨组累加）仍未修

## 五、磁盘重复 id 时删除残留（🟠 新发现）

### 机制

`remove()` 用 `findIndex` 只删**第一处**（`store.ts:144-148`），而 `load()` 会把同 id 的多行都收进 `entries`（`store.ts:71-78` 无 id 去重）。若磁盘因历史遗留/手工编辑/早期并发产生同 id 两行：

### 实测

```
load 后内存条目数      : 2（磁盘 2 行同 id）
remove 后磁盘内容      : ["dup-payload"]
判定 删除是否彻底      : ★ 残留 1 行 —— 用户看到"删除成功"但条目还在
重新 load 后条目数     : 1
```

删除回执是**成功**的，但条目在界面上消失、重新加载后又回来。用户会认为"删除不生效/记忆自己复活"。

### 建议

`load()` 按 id 去重（保留 `updatedAt` 较新者，与合并规则一致），或 `remove()` 删除**所有**同 id 行。推荐前者——顺带让 `revision()` 与 `byId()` 不再有多行歧义。

## 六、注入回调静默吞异常（🟡 新发现）

`src/index.ts:53-58`：

```ts
text: (c) => {
  try {
    const cwdRaw = (c as AgentLike).agent?.session?.header?.cwd
    return renderSnapshot(store.snapshot(), cfgRef(), cwdRaw ? normalizeScope(cwdRaw) : '')
  } catch { return '' }
},
```

`renderSnapshot` 抛出的任何异常都变成"本回合注入空串"，**无日志、无计数**。结合本报告问题一/二（合并、重读都在此路径附近），一旦将来引入读盘逻辑，读失败会被静默吞成"没有记忆"，而用户与 agent 都无从察觉。

对照：`index.ts:57` 之外，快照注册失败路径（`index.ts:68`）**是有 warn 的**——说明作者本有记录意识，此处是遗漏。

### 建议

`catch` 内至少 `ctx.logger('local-memory').warn(...)`；或返回一条可见的降级提示行（如 `(local-memory: snapshot render failed — see host log)`）。符合全局协议第 8 条「观测性回写」。

### 补充实证（含一次我自己的误报更正）

我一度怀疑描述符挂载点错误（探针打印 `remoteMethods()` = `[]`），复核宿主实现后确认是**我的探针用错 API**：

```js
function remoteMethods(service) {
  const prototype = Object.getPrototypeOf(service);   // ← 参数是「实例」，取原型
  ...
}
```

正确调用（传实例）返回正常：

```
remoteMethods(实例) = [{"method":"call","invocation":{"kind":"direct"}}]
宿主键名 === 我方键名 : true
```

**`remote.ts` 的挂载点是对的，我撤回该疑点。** 但这恰好说明注释里承诺的那个测试**应当存在**——它能防止将来上游改键名时静默失联。

### 建议

补 `test/remote.test.mjs`：用宿主真实的 `remoteMethods()` 读 `LocalMemoryRemoteService` **实例**，断言 `call` 可见；并对 `src/client.ts` 的负载形状（`{args:{endpoint,payload}}`）做契约断言。
