## 一、跨进程删除复活（问题 1）

### 根因

`mergeFromDisk()` 是**纯并集**：本地内存持有的条目，即使磁盘上已被对手删除，也会在下一次 flush 时被原样写回。`tombstones` 是实例字段、不跨进程，管不到对手。

### 修法

引入 `knownOnDisk` 集合，区分两种"本地有、磁盘没有"：

- **曾落过盘** ⇒ 对手删了它 ⇒ **跟随删除**（本次修复）
- **从未落盘** ⇒ 本地刚 `add`、还没写出去 ⇒ 保留（否则新条目会被自己的合并逻辑吃掉）

`flush()` 成功落盘后重建 `knownOnDisk`（此刻磁盘内容 == 内存内容）。

### 验证（独立探针，真实 spawn）

```
A 删除后磁盘: []
最终磁盘: ["B-新条目"]
判定 删除是否被复活 : 未复活     ← 修复前为 ★ 复活了
```

## 二、读路径永久陈旧（问题 2）

### 根因

`mergeFromDisk()` **只在 `flush()` 内**被调用 ⇒ 只有写操作才重读磁盘。纯读（每轮注入 `renderSnapshot`、`local_memory_search`）在进程生命周期内永远看不到对手的写入。

### 修法

`snapshot()` 前加 `refreshFromDisk()`：以 `mtime:size` 作磁盘签名，**签名未变则直接返回**（热路径零额外 IO），变了才在锁内重读合并。读路径拿不到锁时**不抛错**——沿用内存副本、下次读再试，避免把并发压力转嫁到注入路径上。

### 验证（独立探针，真实 spawn）

```
B 首次 load 条目数 before=1
A 写入后 B 再读条目数 after=2  revision=92b96e379255   ← 修复前为 1
判定 B 是否感知 A 的写入 : 感知到
```

**附带收益**：B 侧 revision 现与 A 侧一致，即核对文档里"乐观锁跨进程失明"那条**同源问题一并解决**（设置页的 `expectedRevision` 现在能看见跨进程写入）。

## 三、P2 写入即失明（问题 3，用户选定方案 A）

### 修法

`render.ts` 的预算裁决改为：**本组第一条无条件保留**。即 `entryMaxChars` 配得再大，写入也不会永远不可见。

配套发现（修复过程中暴露）：强制保留会突破预算，分组头出现 `331/200 chars` 这种读者无法解释的数字。故加了 `, over budget — first entry kept in full` 说明，并为其补了测试。

### 验证

```
add 回执: id=ba733c7203e3  text.length=300
该条是否出现在注入中 : 出现     ← 修复前为 ★ 未出现 —— 写入即失明
```

> 方案 B（配置交叉约束）未采用：它要求把 `maxInjectionChars` 下限从 200 提到 400，属破坏性变更且与 README 记录的区间不符。方案 A 零配置破坏。

## 七、诚实标注

**已修且有实证**：问题 1、2、3、5（真实 spawn / 实机探针）、问题 4（自动比对 + 变异测试）。

**测试级别说明**：
- 问题 7 的 remote 测试是**契约测试**（读宿主真实 reader + 比对键名），非端到端网关调用——真实网关需要跑起宿主进程，本轮未做。

**新增的已知边界**（已写入两版 README）：
- 两个进程**同时编辑同一条**时按 `updatedAt` 裁决，失败一方的修改被丢弃且无提示——这是剩余的暴露面，本轮未修（需要更复杂的冲突检测或用户可见的冲突提示）。
- 强制保留首条会使该组突破 `maxInjectionChars`（条内不截断是 spec 冻结决策）；已用 `over budget` 标注使其可见。
